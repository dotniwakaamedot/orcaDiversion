# ファイルで連携する4役エージェント

| 役割・定義                                                           | 担当                                 | 書き込み先                 |
| -------------------------------------------------------------------- | ------------------------------------ | -------------------------- |
| [progress_manager](../.codex/agents/progress_manager.toml)           | 計画、割当、依存、状態、改善案の採否 | 計画・依頼・回答・判断記録 |
| [task_worker](../.codex/agents/task_worker.toml)                     | 割当範囲の実装と検証                 | 所有する成果物・結果・質問 |
| [verification_reviewer](../.codex/agents/verification_reviewer.toml) | 計画・成果物の独立した確認と合否     | 確認レビュー・質問         |
| [progress_reviewer](../.codex/agents/progress_reviewer.toml)         | 進行上の問題、改善案、Skill提案      | 進行レビュー・質問         |

親エージェントが進行管理を担い、最終的な範囲・統合・ユーザーへの報告に責任を持ちます。成果物の作者と確認レビュー担当は別エージェントにします。進行レビューは成果物の合否を代行しません。既存の [task_cleanup_checker](../.codex/agents/task_cleanup_checker.toml) が最後に整理候補を確認し、親は [完了チェック手順](task-cleanup-check.md) に従って不要と確認できた worktree、ブランチ、一時ファイル・フォルダーを削除します。

定義形式は [OpenAI公式 Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) に従います。モデル・推論設定・権限は親から継承します。ファイルによる所有範囲の指定は運用上の契約であり、OSのアクセス制御を追加するものではありません。

## 共有場所と所有権

1回の作業ごとに `docs/agent-runs/<run-id>/` を作ります。全担当へ同じ共有場所の**絶対パス**と自分の作業場所を渡します。別worktreeでも共有runは複製しません。`run-id` は日時と内容などで重複を避けます。Gitの作業場所は依頼で指定し、単一checkoutでの同時ブランチ切替は行いません。

```text
<shared-run>/
  plan.md                           # 管理だけが更新
  tasks/01/request-01.md             # 管理 → 作業
  tasks/01/result-01.md              # 作業 → 確認レビュー・管理
  tasks/01/review-request-01.md       # 管理 → 確認レビュー
  tasks/01/review-01.md               # 確認レビュー → 管理
  questions/01-question-01.md         # 質問者だけが作成
  questions/01-answer-01.md           # 管理だけが作成
  process/review-request-01.md        # 管理 → 進行レビュー
  process/review-01.md                # 進行レビュー → 管理
  process/issues/P01.md               # 進行レビュー → 管理（Issue本文案）
  process/issue-registration-01.md    # 管理 → 関係担当（Issue URL・登録結果）
```

各ファイルの書き手は1人です。役割名だけでなく実行中の担当エージェントIDも計画と依頼に記録します。タスクごとの実装ファイルの所有範囲も指定します。共有状態表と採否の記録は管理だけが更新し、作業担当は結果へ状況を書いて引き渡します。他者の変更は取り消しません。

チャットや通知ツールは**確定したファイルパスの通知だけ**に使い、指示、質問、回答、判断、結果はファイルを正本にします。受信者は通知先のファイルを読んでから行動します。口頭だけで範囲や合否を変えません。機密・トークン・不要な個人情報は記録しません。

書きかけは同じディレクトリの `.tmp` ファイルへ保存し、完成後に確定名へrename/replaceして公開します。読み手は`.tmp`を読みません。確定した依頼・結果・レビュー・質問/回答は上書きせず、新版を別名（`request-02.md`等）で公開します。管理の`plan.md`は単独所有で置換更新し、過去の判断と版への参照を残します。

## 作業の流れ

1. 管理が [planテンプレート](agent-workflow/templates/plan.md) を共有runへコピーし、目標、完了条件、対象外、権限、担当ID、依存、作業場所を埋めます。状態は`未着手`、`着手`、`終了`の3つだけとし、ブロッカーやレビュー待ちは別欄へ記録します。
2. 作者とは別の確認レビュー担当に計画を渡します。レビュー依頼は対象計画の版と内容を識別するSHA256を含めます。blockingがなく承認された計画で作業を割り当てます。
3. 管理が [task-request](agent-workflow/templates/task-request.md) を作成し、依存完了を確認して状態を`着手`へ変えます。共有ファイル、スキーマ、設定が重なる作業は直列にし、並行時は所有範囲とworktreeを分離します。
4. 作業担当が指定範囲を実装・検証し、[work-result](agent-workflow/templates/work-result.md) を公開します。結果には未追跡も含む変更対象のSHA256、削除対象、検証の作業ディレクトリ・コマンド・終了コード・結果・証跡を含めます。未実施は未確認と書きます。提出後はレビュー対象の変更を止めます。
5. 管理が結果の版とSHA256を指定したレビュー依頼を作ります。別担当が実ファイルと証跡を確認し、[verification-review](agent-workflow/templates/verification-review.md) へ承認/要修正を記録します。レビュー用の一時出力は製品ファイルから分離します。
6. 要修正なら管理が次版の作業依頼を作り、対象の修正後に結果・レビューも新版にします。承認は対象版限定です。HEADが同じでも未コミット差分が変われば旧承認は使いません。計画・成果物のレビューはそれぞれ同じ対象で最大3回までとし、blockingが残れば`着手`のまま理由を記録して相談します。3回到達で自動承認しません。
7. 管理が完了条件、対象版の承認、検証、必要な統合を確認して`終了`へ更新します。節目・停滞・反復する手戻り・最終時には進行レビューを依頼します。
8. 管理が進行レビューの提案の採否と次の作業を記録し、親タスクの最後に既存の完了後整理チェックを一度行います。補助担当の完了ごとには起動しません。

変更ファイルの識別例（PowerShell、対象は割当のファイル一覧から指定）:

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath '.codex/agents/task_worker.toml'
git rev-parse HEAD
git status --short
```

HEADや`git diff`だけでは未追跡ファイルを特定できないため、変更対象の実内容をSHA256で照合します。削除対象は結果にパスと削除を明記し、レビューで不存在を確認します。報告・計画自体が対象ならその確定版のSHA256も依頼側へ記録し、同じファイル内に自分自身のハッシュを埋め込みません。

## 進行レビューとSkill提案

管理は対象期間・依頼/結果/レビューのパス・質問事項をファイルへ書いて依頼します。[progress-review](agent-workflow/templates/progress-review.md) に、事実と原因仮説を分けて記録します。

改善案は問題の根拠、優先度、具体案、期待効果、費用・リスク、次担当、効果確認方法を持ちます。Skill提案は現在利用可能なSkillの所在を確認し、既存Skillの活用を優先します。新規Skillは既存で足りない反復作業に限って候補とし、名前・場所・適用条件・対象外・重複・小さな試行の検証を付けます。問題や提案がなければ、なしと根拠を書きます。

管理は`plan.md`の判断記録で提案IDごとに`採用`/`保留`/`見送り`、理由、次担当、実施状況、効果確認結果を追跡します。範囲内の改善は具体化して作業へ戻し、新しい権限が必要なものだけユーザーへ確認します。提案そのものはSkillの作成・インストール、設定やAGENTS.mdの変更を許可しません。

### 提案をIssueへ登録する

進行レビューの改善案・Skill提案は**採用/保留/見送りにかかわらず全件**を登録対象とします。対象リポジトリへの登録権限を確認し、許可がない場合は本文案を保持して未登録と記録します。Issue登録は実装やSkill導入の承認を意味しません。提案なしの場合はIssueを作りません。

進行レビュー担当は各提案に `<run-id>:<確定レビュー名>:<提案ID>` の識別キーを付け、[Issue本文案テンプレート](agent-workflow/templates/issue-proposal.md)で1提案1ファイルを `process/issues/` に保存します。本文案には提案元・確定版SHA256、根拠、優先度、具体案、期待効果、費用やリスク、次担当、採否・実施状況、検証可能な完了条件を含めます。公開先に不要な個人情報や資格情報を含めず、未コミットの提案元には存在しないGitHubリンクを作りません。

登録担当は進行管理だけです。利用先の認証手順で認証し、open/closed両方のIssueを識別キーと内容で調べます。同じ提案があれば既存Issueを参照し、再実行で重複作成しません。識別キーを `<!-- progress-review-proposal:<識別キー> -->` としてIssue本文に含め、構造化引数または `gh issue create --body-file` で登録し、APIで本文・URLを読戻します。既存Issueの再オープン・コメント・closeはこの登録には含めません。

管理は[Issue登録記録テンプレート](agent-workflow/templates/issue-registration.md)へ本文案・識別キー・URL・登録/読戻し結果を保存し、plan.mdにも提案IDとURLを記録します。確定した進行レビュー本文を登録後に書き換える必要はありません。認証・登録失敗は未登録として残し、作成応答の不明時は成否未確認と記録します。識別キーで再照合できるまでは再作成せず、未解決の登録を完了扱いにしません。

## 質問・差し戻し・再開

- 質問は [question-answer](agent-workflow/templates/question-answer.md) の質問欄を別ファイルへ作り、管理は回答を別ファイルへ作ります。質問者の確定ファイルは編集しません。待つ必要がある範囲と進められる作業を区別します。
- 例: `request-01 → result-01 → review-01(要修正) → request-02 → result-02 → review-02(承認)`。どの指摘をどの版で直したかを記録します。
- 再開時は管理が`plan.md`と最新の確定ファイルを読み、旧担当の終了・中断などにより**書き込みが止まったことを確認してから**担当IDを変更します。確認できない所有範囲へ別担当を同時投入しません。
- 現在のファイルのSHA256と依存を再確認し、新版の依頼に再開地点・残作業・新担当IDを記録します。古い担当へ戻す場合も新版を使います。中断を成功扱いしません。

## 起動例と認識確認

ユーザーから親への依頼例:

> 進行管理・作業・確認レビュー・進行レビューの4役で、この修正を進めてください。共有場所をdocs/agent-runsに作り、指示と結果はファイルで引き継いでください。

管理は共有runの確定ファイルの絶対パスを担当に通知します。

定義が認識された環境では各役名を指定して起動します。このセッションに新しい役が表示されない場合は、通常サブエージェントへ「対応する定義ファイル、手順書、依頼ファイル」を読むよう指定して代替します。次の新しいCodexセッションで4役を選択できるか確認してください。定義の配置だけでは常駐・監視・定期起動は始まりません。新セッションでの認識確認をしていない場合は、その旨を未確認として残します。
