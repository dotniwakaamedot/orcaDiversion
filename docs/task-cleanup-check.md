# タスク完了チェック

このリポジトリで Codex が Issue または独立したタスクを完了する際、親エージェントが最終報告前に `task_cleanup_checker` を一度起動する。承認・マージ待ちなどで未完了の Issue や補助担当の途中終了では、再開に必要なものを保持し、重複してチェックを起動しない。起動ルールは [AGENTS.md](../AGENTS.md)、担当の定義は [.codex/agents/task_cleanup_checker.toml](../.codex/agents/task_cleanup_checker.toml) に置く。

これは AGENTS.md によるタスク完了手順であり、OS の常駐サービスや GitHub のイベントフックではない。Codex を介さない作業や強制終了では実行されない。専用エージェントの設定を読み込むには、このリポジトリで新しい Codex セッションを開始する。既存セッションでは通常のサブエージェントに定義と手順を読ませて実行できる。

## 親からの引き渡し

- 完了タスク、対象 Issue/PR の番号または URL
- 作業ブランチ、コミット、マージ状況
- 検証結果、残作業、既知の制約
- 他の担当が使用中のブランチ/worktree
- 作業中に作成した一時ファイル・フォルダーの絶対パス、用途、作成者、必要な期間と保存先。成果物・証拠や他の担当の使用対象も明示する

不明な項目は「不明」とする。チェック担当の結果を待ち、親が削除の可否を再確認してから必要な整理を実行する。

## 確認手順

最初に作業対象の管理方式とサービスを確認する。Git リポジトリと確認できた場合だけ Git 固有の手順を行い、GitHub を利用すると確認できた場合だけ GitHub の認証と照合を行う。Diversion など非 Git の作業対象では worktree・Git branch・GitHub PR の確認は該当外として記録し、該当する一時物の確認（手順6）を行う。管理方式や対象が不明な場合は該当項目を未確認とし、推測して Git・GitHub 操作しない。

候補の報告は読み取り専用で行う。候補であることは削除・Issue close の権限を意味しない。各操作の対象・内容と利用先の適用指示・ユーザーによる認可を確認し、認可または対象の範囲が不明なら操作せず保留する。未コミット・未追跡・ignored を含む未保存物の削除は、対象の絶対パス、Issue との関係、所有者・利用状況、削除される内容と、その未保存物を含む削除が認可されていることを個別に確認する。

1. チェック担当は `git status --short`、`git branch --show-current`、`git worktree list --porcelain`、`git for-each-ref refs/heads refs/remotes/origin` で作業状態を読む。worktree ごとの未コミット変更、未追跡・ignored ファイル、ロック、他の担当の使用状況も確認する。チェック担当は状態を書き換えない。
2. GitHub 認証は利用先の AGENTS.md と認証設定に従う。資格情報を表示・保存せず接続を確認し、環境変数を一時設定する場合は finally で以前の状態へ戻す。接続確認に失敗したら結果を報告し、GitHub の確認・リモート削除は保留する。
3. `gh repo view --json nameWithOwner,defaultBranchRef` で対象リポジトリと既定ブランチを確認する。`gh api --paginate` でリモートのブランチ、オープン Issue（PR は除外）、オープン PR を取得する。関連するマージ済み PR、Issue 本文・コメントは必要なものだけ読む。件数を制限した場合は確認範囲と未確認分を明示する。
4. ローカルブランチの先端 SHA と最新の既定ブランチ SHA を照合する。リモート API の compare や PR 情報も利用し、ローカルの追跡参照が古ければ「未確認」とする。squash/rebase マージは祖先関係だけで判定できないため、PR のマージ記録と現在の先端 SHA の一致、追加コミットの有無を確認する。
5. Issue は今回のタスクとの関連を優先して調べる。状態ラベルを問わず、Issue を完了させる PR のマージ先・状態と Issue との関係を確認する。単なる言及や部分対応は対象外。自動 close が行われていなければ、親は手動 close の認可が確認できた場合に限り close し、結果を読戻す。認可不明、確認や更新に失敗した場合は未完了として報告する。
6. 親から渡された一時ファイル・フォルダーの一覧と作成記録を照合し、実体と内容、使用者、再開・検証・保管への必要性を確認する。名前、拡張子、古さ、ignored であることだけを根拠に一時物や不要物と判定しない。範囲や内容を確認できないものは保留する。

## 判定基準

| 対象                     | 候補にできる条件                                                                                                                                                                                                                                    | 保留する条件                                                                                                                                                                                                           |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| worktree                 | 閉じた Issue に関連する worktree は作業終了、所有者・対応関係と内容を確認して候補とする。未コミット・未追跡・ignored も内容を確認する。その他は不要と確認でき、未保存データがなく統合済み、または下記の定期 Issue worktree の未統合特例を満たす場合 | 現在の checkout、使用中、所有者・利用予定が不明、ロック中、状態不明は保留し、確認後に再試行する。閉じた Issue に関連する worktree 以外は保持すべきファイルや未統合の変更がある場合も保留。いずれも削除は別途認可が必要 |
| 一時ファイル・フォルダー | 作業のために作成したことと所有者の終了が確認でき、保存・再開・検証・他の担当に不要                                                                                                                                                                  | ユーザーデータ、成果物、証拠、ログ、共有 run、使用中、内容・所有者・用途・必要性が不明                                                                                                                                 |
| ローカルブランチ         | 全変更が既定ブランチへ統合済みで、追加コミット・利用予定がない                                                                                                                                                                                      | 現在のブランチ、別の worktree に割り当て済み、他の担当が使用中、未マージ、用途不明                                                                                                                                     |
| リモートブランチ         | 最新の先端まで統合済みで、保護・継続利用・オープン PR がない                                                                                                                                                                                        | 既定/保護ブランチ、release 等の継続利用ブランチ、未マージ、追加コミット、オープン PR、保護状態不明                                                                                                                     |
| オープン Issue           | ラベルにかかわらず、その Issue を完了させる PR のマージを確認                                                                                                                                                                                       | 部分対応・単なる言及、未マージ、対応関係や状態が未確認                                                                                                                                                                 |

すでに閉じている Issue はクローズ候補から除外する。古さ、ブランチ名、コミットメッセージ、`Closes #...` の記載だけで候補にしない。放棄・重複は根拠がある場合だけ別の整理候補として報告し、実装完了とは区別する。ブランチ削除と worktree の削除は別の操作として扱う。所有者の終了や継続利用予定が確認できないことを、不要である証拠としない。

## 定期 Issue worktree の未統合特例と監視

対象は共有 run に Issue・run ID・所有者・ブランチ・絶対パスが記録された定期 Issue 専用 worktree に限る。PR 承認・マージ待ちでも、担当全員の終了と書込み停止、再開に必要な内容・検証証拠の worktree 外への保存、ローカル HEAD と認証済みリモートの実際の対象ブランチ先端 SHA の一致、再開情報（Issue、PR、ブランチ、SHA、未完了事項、保存先）の記録を確認でき、未コミット変更・保持すべき未追跡/ignored ファイルがない場合は worktree のみ削除候補にできる。既存ブランチは別判定で保持する。push 不明、終了不明、保存先や内容不明、ロック中は保留。ignored ファイルを含む全内容を確認できなければ保留し、通常 status が空であるだけでは安全としない。

親は削除直前に上記の条件、対象の実体・所有者・ロック・HEAD とリモート先端を再照合し、状態変化や失敗があれば保留する。再開時は旧担当の終了、共有 run・保存先・ブランチ先端を照合し、必要なら対象ブランチから専用 worktree を作成する。現在の作業基準ブランチ取込み・再検証の既存ルールは維持する。

定期実行の親は runner が指定した実行記録ディレクトリに `worktree-cleanup.md` を保存し、対象ごとの run ID、Issue、パス、ブランチ、HEAD、保存・担当終了・再開情報・削除前確認の根拠、削除済み/保留/失敗、理由、次の対応を記す。秘密は記録しない。対象なしも明記する。前回までの記録と `status.json` を照合し、未終了・記録欠落と保留の継続回数を記載する。同一理由の3回連続保留、削除失敗、記録欠落は報告で目立たせる。対象数・削除数・保留数・失敗数と開始時/終了時の定期 Issue 専用 worktree 数を記録し、週次で推移を確認する。過去の所有不明 worktree を名前・古さだけで削除対象にしない。次回の再確認でも終了や保存を証明できなければ保留する。

runner は終了後に記録の有無を独立して確認し `cleanup-monitor.json` に記録する。欠落は未確認であり整理成功ではない。突然の停止では終了処理自体が動かないため、次回に未終了状態を検知する。runner が停止したままの場合を検出するには外部監視が別途必要。

## 親による削除

チェック担当の結果を受けた親は、各対象の削除について利用先の適用指示とユーザーによる認可を確認する。必要な認可が既にある場合に限り追加指示を待たずに実施し、認可が不明・不足の場合は対象と内容を示して保留する。削除する直前に対象の絶対パス・ブランチ名・先端 SHA、使用者、未コミット/未追跡/ignored ファイル、ロック、最新の統合状況・オープン PR・保護状態を対象ごとに再確認し、変化や不明点があれば保留する。Git 固有の操作は対象が Git と確認された場合のみ実行する。現在の checkout、利用先で保護された基準ブランチ、既定ブランチ、保護ブランチは削除しない。

1. worktree は Git が管理する絶対パスと削除の認可を確認して `git worktree remove <絶対パス>` を使用する。閉じた Issue に関連する worktree では未保存データを含む全内容、Issue との対応、所有・利用終了と未保存物を含む削除の認可を確認し、必要な場合に限り `--force` を使う。いずれか不明なら保留する。その他の worktree では保持すべきファイルが残る場合や強制削除が必要な場合は保留する。直接の再帰削除と一括 `prune` は使わない。Windows では削除対象の絶対パスが意図した worktree 内であることを事前確認する。
2. ローカルブランチは、worktree が解除され、先端と統合状態が変わっていないことを確認して `git branch -d <名前>` を使用する。Git が拒否した場合は強制せず、理由を報告する。
3. リモートブランチは、最新の先端まで統合済みで、保護・継続利用・オープン PR がないことを GitHub で確認する。削除時は確認した SHA から先端が変わっていないことを条件にした Git の lease を使用し、失敗時は上書きせず保留する。認証・保護状態・利用状況・統合状態が確認できない場合は削除しない。
4. 一時ファイル・フォルダーは、作業のために作成された個別対象と判明し、内容・利用終了・保管不要を確認できたものを削除する。削除直前に実体の絶対パス、許可された書き込み範囲、フォルダー内の全内容とリンク先を再確認し、意図した対象の外へ出るリンクや判断できない内容があれば保留する。Windows では同一 PowerShell セッションで対象を検証し `Remove-Item -LiteralPath` を用いる。再帰削除は最終的な絶対パスが意図した対象内にあることを確認した場合に限る。ワイルドカードや拡張子・名前だけによる一括削除はしない。

Issue のクローズは上記の完了 PR のマージと認可を確認した場合に限り親が実行する。PR の変更とコメント投稿はこの手順に含めない。削除に失敗しても元のタスクの成果とは分けて報告する。

## 報告形式

- 削除した worktree とブランチ: パスまたはローカル/リモートの名前、先端 SHA、統合と利用終了の根拠。削除なしも明記。
- 削除した一時ファイル・フォルダー: 絶対パス、作成目的、不要と判断した根拠。対象なしも明記。
- Issue クローズ候補: 番号、URL、条件ごとの完了根拠、関連 PR/コミットと検証結果。
- 保留: 対象と残作業・不足情報。
- 確認範囲: 確認日時、既定ブランチと SHA、認証結果、未確認項目。

候補なしの場合も明記する。認証・取得失敗は「未確認」とする。チェック担当は候補の報告までを担当し、親が削除とその結果確認を行う。

設定形式と委譲の仕組みは [OpenAI 公式ドキュメント](https://learn.chatgpt.com/docs/agent-configuration/subagents) に準拠する。
