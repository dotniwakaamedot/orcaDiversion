# GitHub Issue の運用

この手順は Git/GitHub リポジトリで、実行主体が利用先の設定、適用指示、個別の権限を確認して使う。設定例だけでは、Issue 作成・編集、コメント、push、PR、マージ、close、削除や定期実行の許可は得られない。権限または必須情報が未確認なら対象操作を保留する。連携の技術的条件は [Git/GitHub 連携](adapters/git-github.md)、担当の引き継ぎは [Agent ワークフロー](agent-workflow.md) を参照する。

## 起票・詳細化・状態

1. Issue には背景、確認した事実と仮説、根拠と参照先を区別して記す。不具合では確認できた対象版・環境、再現手順、期待/実際、ログ・原因調査を付ける。未確認事項と追加調査を明記し、推測を事実にしない。
2. 起票後に関連実装・テスト・Issue を調査し、目的・対応案・検証可能な完了条件・必要な検証を本文に整理する。判断に必要な情報や本文更新が不足する場合は着手せず、調査範囲・不足・次の調査を記録する。調査自体が目的でも範囲・成果の完了条件を決める。
3. 状態ラベルは原則1つとし、調査・詳細化中 `status:refining`、完了して待機 `status:ready`、計画・実装着手 `status:in-progress`、PR承認待ち `status:awaiting-review`、保留 `status:blocked` とする。詳細化中の保留から再開する場合は refining、引継ぎを確認した実装再開は in-progress に戻す。利用先で別名を指定する場合は対応表を明示する。
4. 状態ラベル以外は保持する。ラベルの更新は API で読戻し、失敗・不明を記録する。必要なラベルがなければ同名の既存ラベルを確認後、権限がある場合だけ作る。

## 二重着手と進行記録

着手・再開前に Issue、全状態ラベル、全ページの関連コメント、open PR、共有 run、worktree と担当を照合する。ラベルがなくても PR や記録があれば未着手と決めつけない。進行中の他担当、矛盾や所有者不明が解消しなければ保留する。

親または進行管理は権限確認後に状態を in-progress にし、run ID、一意な event ID、UTC 時刻、担当、範囲、予定ブランチをコメントする。コメント識別子 `<!-- issue-progress:<run-id>:<event-id> -->` を入れ、送信成否が不明な場合は全ページを識別子で照合するまで再投稿しない。ラベルとコメントの両方を API で読戻し、片方でも確認できなければ実装しない。読戻し直後、計画・実装開始前にラベル、全コメント、関連 PR、run と担当を再照合し、新たな競合・所有者不明・照合失敗があれば停止する。

ラベルとコメントは排他ロックではなく同時着手を完全には防げない。同一状態領域の runner ロックを維持し、共有ロックがないだけでは保留理由にしない。開始後に重複を発見した場合は停止して成果物を保護し、担当・引継ぎ・再開条件を記録する。時間経過だけで所有権を奪取しない。

ブランチ作成、PR 作成、保留、再開、承認、終了・close などの節目で、確認済みのブランチ、PR URL、対象 SHA、検証、残作業、理由・再開条件を記録する。秘密、不要な個人情報やローカル絶対パス、実在しないリンクは投稿しない。進行中の記録失敗時は変更を保護し、照合と復旧まで保留する。

## 計画、作業、再開

- 依存、対象範囲、完了条件、所有範囲、基準 SHA、検証を計画し、不変の snapshot を保存する。作者と別の担当が実資料を独立に読み、SHA256 と指摘を照合する。変更すれば新版を発行し再レビューする。定期 Issue の計画・成果レビューは指摘なしまで進め、同じ意味の指摘が2回出た場合、または最大3回で未解決の場合は自動承認せず停止・記録する。
- 承認済みの作業基準コミットから Issue ごとに新規の作業ブランチと専用 worktree を作成する。既存作業・未コミット内容を保持し、同一 checkout の並行切替や元 checkout・基準ブランチへの直接実装をしない。実装者は未追跡を含めた対象ファイル SHA256、削除、実行場所・コマンド・終了コード・証拠を記録し、別担当が実ファイルと突き合わせる。
- 再開時は旧担当の停止と所有権、変更・保存、基準・対象版を確認する。基準の新しいコミットが作業ブランチに含まれない場合、保護可能な変更を保存した上で基準を取り込み、競合を解消して対象版のテストと独立レビューをやり直す。所有者不明・保護不能は触らず保留する。基準がリモートより遅れ・分岐、または最新状態を確認できない場合は判断を保留する。

## PR と Issue の終了

親子関係と対象リポジトリを GitHub で確認し、サブ Issue は親ごとの統合ブランチへの PR とし、標準連携を使う場合は本文に単独行で `Sub-issue: #<番号>` を1つ記す。親・単独 Issue は指定の最終 base を対象とし、必要に応じ `Closes #<番号>` を記す。既定ブランチ以外へのマージでは標準の自動 close を前提にしない。

PR head・レビュー・検証・マージの実状態を追跡し、自己承認や承認の偽装をしない。PR 作成後は awaiting-review、承認後のマージ待ちはそのラベルを外し、承認対象 SHA と未マージを記録する。PR のマージには適用指示に基づく権限が必要。マージ後は Action の実行結果と Issue 状態を確認し、完了 PR と Issue の対応が確認できたのに自動 close されなければ許可の範囲で手動 close して読戻す。部分対応・単なる言及は対象外。失敗や未確認は未完了として報告する。

## 進行レビュー提案

別担当が節目・停滞・反復する手戻り・最終時に根拠と原因仮説を分けて評価する。改善案・Skill 提案は採否にかかわらず1提案1本文案とし、提案元 SHA256、識別キー、期待効果・費用・リスク・完了条件を記録する。既存 Skill を確認し、提案だけで導入・変更しない。

進行管理は適切な対象と権限を確認して open/closed の既存 Issue を識別キーと内容で全ページ照合する。同一提案は既存 Issue を参照し、新規作成した場合は本文と URL を読戻して共有計画と登録記録に保存する。応答不明なら照合まで再作成しない。許可・認証がない場合は本文案を残し未登録として報告する。提案なしなら登録しない。Issue の作成は実装や Skill の導入を許可しない。

完了後の候補確認は [タスク完了チェック](task-cleanup-check.md) に従い、親が一度だけ起動する。認証失敗や確認不能を候補なし・成功と混同しない。
