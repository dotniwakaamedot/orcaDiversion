# GitHub Issue と共同作業の共通手順

## 設定と権限

適用先の AGENTS.md とユーザー指示を優先し、実際のリポジトリ、Git の基準・提出先、Issue 番号、共有 run の絶対パス、認証、テストと担当を確認する。Git と GitHub の接続や権限が確認できない作業は保留する。設定例や本 Skill の存在は外部投稿、push、PR、merge、削除を許可しない。秘密をログや作業記録に記載しない。

## Issue と着手

1. 既存 Issue、実装、テストと関連 PR を調査し、事実・推測を区別する。不具合では確認できる対象版・環境、再現、期待と実際、根拠と不足事項を記録する。本文を目的・背景、対応案、検証可能な完了条件へ詳細化し、不足が着手や検証を妨げるなら着手しない。
2. 状態は通常 status:refining、status:ready、status:in-progress、status:awaiting-review、status:blocked を使う。名称は適用先の指示に従う。他種のラベルを保持し、変更・コメントは読戻す。失敗や読戻し不明は未確認とし作業を進めない。
3. 着手・再開前と着手記録の直後にラベル、コメント、関連 PR、既存 run、担当を照合する。競合が確認されたら保留する。ラベルとコメントは排他ロックではなく、同時着手の完全防止を保証しない。
4. 許可された場合に、承認済み計画の対象 SHA から専用作業ブランチ・worktree を用意し、他者の作業や既存の未保存物を保護する。対象のリモート情報と現在の基準を確認し、適用先指示に従う。再開は旧担当の停止、所有、保存と対象版を確認し、基準変更後に再検証と独立レビューを行う。

## 共有 run と独立レビュー

親が共通 run と完了条件、担当 ID、各ファイルの所有、依存、作業場所と権限を指定し、状態表を単独で更新する。指示、質問・回答、結果、レビューと判断は確定ファイルを正本とし、通知にはその絶対パスを使う。書きかけを一時ファイルへ保存して完成後に公開し、確定済みを上書きせず新版で引き渡す。

計画と成果物は作成者と別の担当が元資料と対象版を独立に確認し、未追跡を含む変更ファイルの SHA256、削除内容、検証コマンド・結果・証拠を照合する。blocking を修正した新版は再検証し、旧承認を使い回さない。各対象のレビューは最大3回で、指摘が残れば保留し報告する。回数到達で自動承認しない。

進行レビューは停滞や手戻りを証拠から確認し、事実と仮説を分け、改善案・Skill 提案の採否と効果を記録する。提案は採否を問わず Issue 登録対象だが、対象リポジトリと実操作の権限を確認する。run と提案を識別するキーで open/closed を照合し、応答不明のときは照合が済むまで再投稿しない。投稿後に読戻す。

## PR と完了

作業内容と現在の head に対する検証・独立レビューを確認し、認可された範囲で PR を作成する。親子 Issue の統合先、関係、承認、base と head、マージおよび自動 close の結果を確認する。未マージ、単なる言及や部分対応だけで Issue 完了としない。完了を目的とする PR がマージされ、自動 close されなければ、対応と権限を確認したうえで close を行い読戻す。マージや外部操作の許可を推測しない。

## 完了後の整理

候補の確認と削除実行は別である。対象の作業場所が Git 管理と確認できた場合だけ Git/GitHub 固有の branch・worktree・PR の状態を確認する。非 Git ではそれらを該当外とし、作業に使用した一時物を確認する。所有者、利用、保存、再開、権限が不明なものや共有 run、成果物、証拠は保持する。名前や古さのみで不要としない。

Git の閉じた Issue に関連する worktree は関連、所有者、作業終了、利用と全内容を確認する。未保存物を含む削除には対象・内容と該当操作の許可を具体的に確認し、不明なら保留する。その他の worktree は未統合・保持すべき変更を保護する。現在の checkout、保護 branch、利用中や open PR の branch は削除しない。各削除と close は親が許可を確認し、実行直前に対象と状態を再照合する。リモート削除は確認済み SHA の変更を検出できる条件を使う。
